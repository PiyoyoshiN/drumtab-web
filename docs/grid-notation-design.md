# Grid 表示の譜面化設計メモ

このメモは、DrumTab Web の Grid 表示を「実用的なドラムタブ」に近づけるための設計方針と確認観点をまとめたものです。高精度な音声分離ではなく、読み込まれた MIDI / JSON / 解析結果を読みやすく整える部分を対象にします。

## 今回の自己レビューで見つけた問題

前回の Grid 改善で小節・拍の表示は入りましたが、実用上は次の弱点が残っていました。

- サンプルのように同じタイミングでクラッシュ、ハイハット、キック、スネア、タムが重なると、各レーンの縦位置が揃っていることを視覚的に確認しにくい。
- `endSec + durationSec + 余白` をもとにステップ数を決めると、最後の小節より余分な小節が表示されやすい。
- 8th / 16th / 32nd の各解像度で「何セルが1拍なのか」が UI 上に明示されていなかった。
- 記号の意味が UI 内に出ておらず、初見で `x` / `o` / `b` / `───` / 大文字 / 括弧の意味を理解しにくい。
- 同一レーン・同一セルに複数イベントが丸め込まれた場合、単純な上書きだけでは情報が失われる。

## 現在の Grid 表示仕様

### 時間軸

- 4/4 を前提に、1小節 = 4拍として表示します。
- `Grid 16th | BPM 120 | 4/4 | 4 cells/beat | 4 bars` のようなメタ情報を先頭に表示します。
- `Bar` 行は小節番号、`Beat` 行は拍番号、`Count` 行はカウントを表示します。
- 小節先頭は `|`、拍先頭は `:`、再生位置は `▶` で表示します。

### 解像度

| Grid | cells/beat | Count 表示 |
| --- | ---: | --- |
| 8th | 2 | `1 + 2 + 3 + 4 +` |
| 16th | 4 | `1 e + a 2 e + a ...` |
| 32nd | 8 | `1 · e · + · a · ...` |

32nd は情報量が多くなりすぎるため、細かい裏拍は `·` で薄く表示する方針です。

### レーンと記号

| レーン | 記号 | 意味 |
| --- | --- | --- |
| `CR crash` | `c` | クラッシュ |
| `RD ride` | `r` | ライド |
| `OH open` | `o` | オープンハイハット |
| `HH closed` | `x` | クローズドハイハット |
| `SN snare` | `s` | スネア |
| `T1 high` / `T2 mid` / `T3 low` | `t` | タム |
| `BD kick` | `b` | バスドラ |
| 空白セル | `───` | ヒットなし / 休符相当 |
| 大文字 | `X` / `S` など | アクセント |
| 括弧 | `(x)` など | ゴースト相当 |
| `+` | `x+` など | 同一レーン・同一セルに複数 hit |

## `public/samples/basic-rock-16th.json` で確認する観点

このサンプルは 120 BPM の4小節パターンです。

- 1小節目冒頭で `CR crash`、`HH closed`、`BD kick` が同じ縦位置に揃うこと。
- 2拍目と4拍目で `SN snare` が読み取れること。
- `HH closed` の 16分刻みが横に追えること。
- 4小節目終盤でハイハット、スネア、タム、キックの同時または近接イベントが、各レーンで同じグリッド上に揃うこと。
- 8th に切り替えたとき、16分の細かさは丸め込まれるが、小節線と拍線は崩れないこと。
- 16th に切り替えたとき、サンプル本来の細かさが最も読みやすいこと。
- 32nd に切り替えたとき、セル数は増えるが `Bar` / `Beat` / `Count` と各レーンの位置関係が崩れないこと。

## 現在の制約

- Grid はテキストベースなので、長い曲は横スクロール前提です。
- 同一レーン・同一セルの複数イベントは `+` で示しますが、正確なフラムや細かい装飾音の表現ではありません。
- 休符は正式な音価ではなく、空白セル `───` として表示します。
- Swing、変拍子、3連符、拍子変更、テンポ変更は未対応です。
- 現状では表示優先であり、編集 UI はまだありません。

## 次に直すべき点

1. 1小節ごとの折り返し表示を追加し、長い曲でも横スクロール量を減らす。
2. レーン名を横スクロール時に見失わないよう、固定表示または小節単位の再掲を検討する。
3. 再生ヘッドに合わせた自動スクロールを追加する。
4. Grid 表示の純粋な文字列生成関数を切り出し、サンプル JSON から 8th / 16th / 32nd のスナップショット確認を自動化する。
5. Swing や 3連符が必要になった段階で、現在の固定サブディビジョン設計を拡張する。

## 2026-05-31 Sprint 更新: 小節ブロック表示

Grid の文字列生成を DOM から分離し、現在は `buildGridRenderModel()` で時間軸・レーン・セルを作り、`renderGridText()` でテキストに整形します。これにより、将来的にサンプル JSON から Grid 出力のスナップショット確認を追加しやすくなりました。

長い曲で横方向に伸び続ける問題を緩和するため、テキスト表示は最大4小節ごとの `[Bars 1-4]` のようなブロックに分けます。各ブロックで `Bar` / `Beat` / `Count` とレーン名を再掲するため、横スクロール中でも小節位置とパートを見失いにくくします。

### サンプル別の確認観点

| サンプル | 主な確認観点 |
| --- | --- |
| `basic-rock-16th.json` | 4小節の基本16分ロック。クラッシュ・HH・BD の同時打音、SN の2拍/4拍、4小節目終盤のタム絡みを確認する。 |
| `eighth-note-groove.json` | 8分主体の基本グルーヴ。8th 表示で `1 + 2 + 3 + 4 +` が自然に読めるか確認する。 |
| `rock-fill-2bar.json` | 2小節目にタム回しとクラッシュ戻りを含む。小節ブロック、タムの縦位置、フィル終端の同時打音を確認する。 |
| `thirty-second-check.json` | 32分の細かい HH/SN/BD を含む。32nd 表示で `1 · e · + · a ·` の粒度が崩れないか確認する。 |

### 現在の自動確認

`npm run check:samples` は以下を確認します。

- 必須サンプルファイルが存在すること。
- 各 JSON が `bpm` と `events` を持つこと。
- 各イベントの `timeSec` / `durationSec` / `velocity` / `drum` が基本的に妥当であること。
- 各サンプルが kick / snare / hihat を含むこと。
- 8th / 16th / 32nd それぞれで、小節数と同時打音ステップ数を算出できること。

### 次の自動化候補

次の Sprint では、`gridRenderModel.ts` と `gridTextRenderer.ts` を Node から直接呼び出す軽量 TypeScript 実行環境、または build 後の JS を利用したスナップショット確認を検討します。現時点では依存追加を避け、JSON 構造チェックを優先しています。

## 2026-05-31 Sprint #5 更新: 長い曲と Grid 自動確認

Grid 表示はデフォルトで4小節ブロックです。先頭メタ情報に `block=4 bars` を表示し、各ブロックは `=== Bars 1-4 / 8 ===` のような見出しを持ちます。8小節以上の曲では次のブロックで `Bar` / `Beat` / `Count` とレーン名を再掲するため、長い曲でも小節位置とパートを追いやすくします。

`GridViewOptions` には将来用に `barsPerBlock` を追加しました。現在の UI では指定していないためデフォルト4小節ですが、将来的には 1 / 2 / 4 小節ブロック切替や、32nd 表示だけ 2小節ブロックにする設計へ拡張できます。

### `long-rock-8bar.json` の確認観点

- 16th Grid で `=== Bars 1-4 / 8 ===` と `=== Bars 5-8 / 8 ===` に分かれること。
- 各ブロックで `CR crash` / `HH closed` / `SN snare` / `BD kick` のレーン名が再掲されること。
- 数小節ごとのクラッシュと、8小節目後半の軽いタムフィルが同じ Grid 上で追えること。
- 8th / 16th / 32nd の切替で例外が出ず、32nd では行長 warning が出ても表示情報自体は生成できること。

### `check:grid` の位置づけ

`npm run check:grid` はブラウザを開かずに全サンプルを 8th / 16th / 32nd で確認します。Node 標準機能だけで動く mirror renderer なので、現在は `renderGridText()` の完全な snapshot test ではありません。確認する内容は以下です。

- BPM / events / kick / snare / hihat の最低条件。
- Grid metadata、`Bar` / `Beat` / `Count`、主要レーン名が出ること。
- 4小節を超えるサンプルで2つ目以降のブロック見出しが出ること。
- 各解像度の bar 数、stacked timing positions、最大行長を算出できること。
- 最大行長が長い場合は warning に留め、32nd 表示の横幅制約として扱うこと。

### Sprint #5 後の制約

- `barsPerBlock` は型と renderer の土台のみで、UI から変更する操作は未実装です。
- `check:grid` は同等仕様の mirror check であり、実 TypeScript renderer の snapshot regression ではありません。
- 32nd の4小節ブロックは横に長くなりやすく、狭い画面では横スクロールが必要です。
